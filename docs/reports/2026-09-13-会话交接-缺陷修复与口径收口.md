## 四、本轮踩到的坑（怎么发现的、怎么绕开）

1. **「方案已定、可直接做」的条目仍要独立验前提**。reader_signals 原定性是「只需换落点」，
   勘察才发现生产端是死的；`status_reporter` 那条待办的前提（影响 project-status）也被实测证伪。
   **两次都是"照做就白做"**。
2. **加闸必须查全部调用点**。钩子硬闸加上后波及 3 处（两个测试夹具、冒烟决策卡、CLI 转发用例），
   漏掉冒烟那处会让 CI 直接红。
3. **Edit 锚点不要用类内方法名**。插测试类时以类内某方法名为锚，把新类插进旧类中间并重复了类头——
   Python 允许重定义，**前一个类被静默覆盖、丢两条既有测试**。同一天在另一个文件又犯了一次
   （插入时切断原用例末两行 → `NameError: proc`，被 RED 运行抓到）。
4. **改文档最大的风险是用新编的命令换旧死命令**。重写 `system-data-flow.md` 时把引用的每条命令
   都在纯 v7 仓实跑核过（含 `promise-ledger` 的 action 白名单）。
5. **先见红再见绿**。冒烟轮 C 的非空断言首轮真的报了「断言失败」并判 BREAK，修好才转 PASS——
   这才证明断言会咬，而不是恰好通过。
6. **测试夹具会掩盖被测对象**。`test_domain_contract` 的 `v7_book` 夹具预建了 `定稿/设定/大纲`，
   用它测「`init_domain_skeleton` 建了什么」会**掩盖**真相（首版即因此失败）；改用裸 `tmp_path`。
7. **Windows 上删 `.git` 要用重命名**：git 对象文件带只读属性，`rmtree` 报 `WinError 5`（F7 老坑）。
8. **CI 静默不触发比红更危险**：workflow 的 `paths` 写错会导致 CI 完全不跑。改 workflow 后
   至少要用 PyYAML 本地解析一遍。
